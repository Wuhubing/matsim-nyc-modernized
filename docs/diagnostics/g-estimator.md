# G 估计器设计说明（草稿，2026-10-18，待用户确认后再动手）

对应总纲 v2（`docs/charter.md`）§3.1 尺子一，以及 §4 方法第 1 步（按 gap 分配试探名额）。

## 1. 要量什么

**一个人的差距**：在第 k 轮的环境下，他能找到的最好方案的估计得分，减去他第 k 轮执行的方案的估计得分。

> gap_i(k) = max_{方案 p ∈ 候选集} Ŝ_i(p | 环境 k) − Ŝ_i(当前方案 | 环境 k) ≥ 0

- **两边用同一个估计器 Ŝ**，同一套路况、同一个打分公式。不能拿"估计的最好方案"去减"真实执行得分"，否则估计器的系统偏差会全部算进差距。
- **环境 k**：第 k 轮的每个路段、每小时的通行时间（`research/link-hours-k`），公交时刻表，收费（政策场景）。
- **打分**：用 MATSim 自己的打分函数（各子人群的参数见 `output_config`）。小汽车出行的时间系数是 0，时间的代价来自活动时间变短（`performing` = 1.747/小时），再加距离费用和收费，所以必须对整个方案重新打分，不能只看出行时间。

**总体**：G(k) = Σ_i gap_i(k) / Σ_i |Ŝ_i(当前方案)|，只算居民（`man`、`nonman`），同时报告：
- gap_i 的中位数、p90、gap ≈ 0（< 0.1 分）的比例；
- 按子人群、收费区相关人群、当前方式分组的 G；
- 各分量（第 2 节）各自的 G。

**两个用途**：
1. **尺子**：G_新方法(停止时) ≤ ε_G，ε_G = 原流程 RQ1 第 99 轮的 G（3 个种子的均值，种子间标准差作为容差）。
2. **信号**：每个人的 gap_i 给方法第 1 步分配试探名额（以后在运行中在线算，本说明只做离线版）。

## 2. 三层（分量），由易到难

| 层 | 分量 | 候选集 | 状态 | 实现 |
|---|---|---|---|---|
| 1 | 选择差距 G_sel | 记忆里已有的方案（最多 5 个），用存储得分 | ✅ 已有，已通过关创新检验（Spearman 0.61，斜率约 1） | `experiments/l2seg/equilibrium_gap.py`（Python） |
| 2 | 路线差距 G_route | 方式、时间不变，每段网络出行换成当前路况下的最优路线 | ⚠️ 有雏形：只覆盖每轮重新找路的约 10%，只算时间，不算距离成本和收费 | 改写为 Java 工具（见第 3 节） |
| 3 | 方式差距 G_mode | 每个子行程换成其他可用方式（各方式用最优路线），其余子行程不变 | ❌ 未建 | Java 工具 |
| （后做） | 时间差距 G_time | 出发时间在 ±30 分钟网格上取最好 | 不做 | — |

**层 2 和层 3 合起来的 G_rm = max(当前方式最优路线, 其他方式) − 当前**，层 3 已经包含了"开车但换路"的改进。报告时按"选择 / 路线 / 方式"分解。

**层 1 的局限**：存储得分是这个方案上一次被执行时的分数，可能过时（O2 的赢家诅咒）；它只是下限，不包括记忆里还没有的更好方案。

### 层 1：选择差距（只要跑现成脚本）

- **数据**：重新规划日志 `replanning-log/agents-k.csv.gz`（每人每轮：执行得分、记忆中最高得分、用的策略）。
- **能算的运行**：RQ1（3）、E1（9）、X1（3）、E3（9，今晚跑完）。W1、W0 没开日志，算不了。
- **工作**：只是提交分析作业。

### 层 2：路线差距

- **对象**：第 k 轮执行方案里所有网络方式的出行（car；FHV、taxi 也是网络方式，路线由系统找，也计入，但单独报告）。
- **做法**：对每段出行，用 MATSim 的找路器（和运行时相同的广义成本：时间 + 距离费用 + 收费）在环境 k 下找最优路线；把新路线代入方案，重新估计到达时间、后续活动时长，再用打分函数给整个方案打分。
- **和现有 `route_gap.py` 的区别**：

| | 现有 | 新版 |
|---|---|---|
| 覆盖 | 只有当轮重新找路的约 10% 的人（比较父代路线和新路线） | 全体开车出行，按抽样 |
| 成本 | 只算时间 | 时间、距离费用、收费，并换算成得分 |
| 对比的是 | 两条路线的通行时间 | 整个方案的估计得分 |

### 层 3：方式差距

- **对象**：每个居民的每个子行程（从家出发回到家的一串出行），按 `SubtourModeChoice` 的规则：
  - 可选方式：pt、car、FHV、taxi、walk、cb、bike、ride（`subtourModeChoice.modes`）；
  - car、bike 是"必须开回来"的方式（链式方式），有没有车按人的属性定；
  - 每次只换一个子行程，其他不变，和 MATSim 自己的换法一致。
- **各方式怎么估**：

| 方式 | 估计方法 | 已知偏差 |
|---|---|---|
| car、FHV、taxi | 找路器 + 环境 k 的通行时间（同层 2） | 每小时平均通行时间比找路器的 15 分钟分段估计偏高约 10%（`route_gap.py` 中位数 1.08–1.12） |
| pt | `SwissRailRaptor`，用运行时同样的公交时刻表和参数 | **看不到拥挤和上不了车**；NYC 模型公交运力不足，估计会偏乐观（见第 4 节 V2） |
| walk、bike、cb、ride | 和运行时一样的直线距离 × 绕行系数（1.4–4.2）÷ 速度 | 和运行时一致，没有额外偏差 |

- **得分**：对每种组合生成一个"估计的执行方案"（出行时间用估计值，活动从到达时开始），用打分函数打分，取最好的。

## 3. 实现

**一个 Java 工具 `GapEstimator`**（放在 `research/rq3-acceleration`，只读数据，不跑交通仿真）：

```
GapEstimator --run 运行目录 --iteration k --sample 0.05 --seed 1 --components route,mode --out gap-k.csv.gz
```

1. 读网络、公交时刻表、车辆、配置（从运行目录的输出文件）；
2. 读第 k 轮的方案快照 `ITERS/it.k/BUILT.k.plans.xml.zst`（取每人被选中的方案）；
3. 用 `research/link-hours-k` 构造一个 `TravelTime`（每路段每小时；没数据的格子用自由流时间）；
4. 按子人群、当前方式分层抽样居民（默认 5%，约 1.9 万人）；
5. 对每人：估计当前方案得分；层 2、层 3 的候选；各自的最好得分；
6. 写出每人一行：person_id、子人群、收费区人群、当前方式、Ŝ_当前、各层最好得分和对应的方式与路线、gap 各分量；
7. Python 脚本 `gap_summary.py` 汇总成 G(k) 和分布，画曲线。

**为什么用 Java 而不是 Python**：
- 公交要用 MATSim 自己的 `SwissRailRaptor`；
- 打分要用 MATSim 自己的打分函数，保证和运行时的分数同一口径；
- 路网有 46.5 万个路段，Python 做时变最短路太慢。

**快照的时间对应**：第 k 轮的快照是第 k 轮重新规划之后写的，被选中的方案就是第 k 轮要执行的方案；环境用第 k 轮的 `link-hours-k`，即这个方案执行时实际遇到的路况。

**以后的运行可以加一个小改动**：让 ResearchMetrics 同时写 15 分钟分段的路段通行时间，消除"每小时 vs 15 分钟"的偏差。这只改输出，不改结果，但要过"开关关闭必须逐位一致"的检查。已有的运行用每小时数据，偏差在两边都有，大部分会抵消，并在 V1 里量出来。

## 4. 验证（看结果之前定好，不通过就不能用）

| 编号 | 检验 | 怎么做 | 通过标准 |
|---|---|---|---|
| V0 | 合成小场景单元测试 | MATSim 的 equil 小路网：方案已经最优 → gap = 0；构造一条已知更快的路线 → gap 等于已知差值；改方式的情形同理 | 全部精确通过 |
| V1 | 估计器和真实得分的一致性 | Ŝ_i(当前方案) 对比第 k 轮实际执行得分（`research/persons-k`） | 报告偏差和 Spearman；Spearman ≥ 0.8，否则先查打分口径 |
| V2 | **能否预测真实改进**（v1 总纲 H0 的标准） | 从重新规划日志里找出第 k 轮之后真的换到估计中最好的路线或方式的人；比较"估计的改进"和"换了之后实际的改进"（执行得分之差） | 路线、方式分别算；**Spearman ≥ 0.3**，报告斜率。方式不通过时，先修公交估计（例如用第 k 轮实际的公交等待时间修正），H1 方法不开始 |
| V3 | 和已有路线差距对齐 | 在 `route_gap.py` 覆盖的那 10% 的人上，新版路线差距和旧版的排序一致 | Spearman ≥ 0.7 |
| V4 | 抽样误差 | 同一快照用不同抽样种子算 3 次 | G 的变异系数 < 5%；否则加大抽样比例 |
| V5 | 合理性 | RQ1 的 G(10) > G(50) > G(99)；关创新后选择差距下降 | 方向成立；不成立要找原因，不能直接用 |

## 5. 要算哪些快照

快照每 10 轮存一次，第 99 轮是最终输出。每条运行取 k ∈ {10, 30, 50, 70, 80, 90, 99}，共 7 个：

| 运行 | 条数 | 快照数 | 回答 |
|---|---|---|---|
| RQ1 基线 | 3 | 21 | 原流程的 G(k)、ε_G 和它的种子波动 |
| E1 基线 | 3 | 21 | 精英父代是否更接近均衡 |
| E3 基线 | 3 | 21 | 同上 |
| X1（只做选择续跑） | 3 | 3（第 49 轮） | 续跑 50 轮后 G 是否继续下降 |

## 6. 工作量和计算量

| 项 | 内容 | 工作量 |
|---|---|---|
| 层 1 | 跑现成脚本：E1、X1、E3 的选择差距 | 0.5 天 |
| Java 骨架 | 读运行输出、构造 TravelTime、抽样、"估计的执行方案"和打分 | 2 天 |
| 层 2 | 路线候选（含收费） | 0.5 天 |
| 层 3 | 方式候选：子行程规则、链式方式、有无车、公交找路 | 1.5–2 天 |

| 生产与写作 | 约 90 个快照、G(k) 曲线、写进 05 和 HTML | 1 天 |
| **合计** | | **约 7–8 个工作日** |

- **每个快照的计算**：载入约 5 分钟（网络、时刻表、方案）；5% 抽样约 1.9 万人 × 平均约 4 段出行 × 8 种方式，网络找路几毫秒一次，公交找路约 10–20 毫秒一次，合计约 15–30 分钟（8 核）；内存约 24 GB。
- **总计算**：约 90 × 0.5 小时 × 8 核 ≈ 350 核时，全部放 `mit_preemptable`，被抢占就重跑单个快照。
- **磁盘**：每个快照的输出只有几 MB。

## 7. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 公交估计偏乐观（看不到拥挤、上不了车） | 方式差距偏大，尤其是换成公交的 | V2 分方式检验；必要时用第 k 轮实际的等车时间修正 |
| 每小时通行时间 vs 15 分钟 | 网络方式的估计偏慢约 10% | 两边同一估计器，V1 量出残余偏差；以后的运行加 15 分钟输出 |
| 只换一个子行程 | 低估需要同时换多个子行程的改进 | 和 MATSim 自己的搜索范围一致，作为定义写明 |
| 不含出发时间 | G 低估时间方面的改进 | G_time 后做；报告时写明 |
| FHV、taxi 没有等车模型 | 估计和运行时一致，但和现实无关 | 不影响"离均衡多远"的定义 |

## 9. 实现与检验结果（10-18）

**代码：** 分支 `research/rq3-gap`（已推送），`GapEstimator`、`PlanEstimator`、`LinkHourTravelTime`、`GapEstimatorSelfTest`、`experiments/rq3/gap_summary.py`。一个快照：载入约 4–5 分钟，5% 样本（16,466 名居民）估算约 2–4 分钟，8 核。

**试跑中修掉的问题：**

| 问题 | 后果 | 修正 |
|---|---|---|
| 快照只有车辆编号，没有车辆 | 找路全部失败，路线差距全为 0 | 按编号补建车辆（类型 = 方式） |
| 8 个线程同时建找路器 | 崩溃 | 先依次建好 |
| 重新规划日志按行号标人 | V2 配不上人 | 按 `persons.csv` 换算 |
| 当前方案的公交也被换成最优班次 | 公交用户被高估；改时间的 V2 斜率 0.01 | 当前方案按原来存的班次（同线路、同上下车站、到站后的第一班）；只有备选方案找最优班次 |

**检验（原版种子 4711，第 50 轮，5% 样本）：**

| 检验 | 结果 | 标准 | 结论 |
|---|---|---|---|
| V0 | 4 项全部精确通过 | 精确 | ✅ |
| V1 | Spearman 0.993，中位误差 0.11 分（公交 0.008，开车 0.009） | ≥ 0.8 | ✅ |
| V2 换路线 | Spearman 0.36，斜率 0.96，n = 282 | ≥ 0.3 | ✅ |
| V2 换方式 | Spearman 0.96，n = 275；按换到的方式，斜率 0.79–1.14，**唯独换成公交 0.48**（估 −25.0，实 −15.3） | ≥ 0.3 | ✅，换成公交偏悲观 |
| V2 改时间 | Spearman 0.76，斜率 0.69，n = 266 | ≥ 0.3 | ✅ |
| V3 | 相对时间差距：本估算器 0.375（第 50 轮）/ 0.22（第 99 轮）；`route_gap.py` 0.23（第 50 轮）、0.22（第 70 轮） | 同量级 | ⚠️ 同量级但不相同：两者对象不同（`route_gap.py` 只看重新找路者随机挑的父方案、用上一轮路况）；逐人比对未做 |
| V4 | 三个抽样种子：G = 0.291、0.281、0.297，变异系数 2.8% | < 5% | ✅ |
| V5 | 第 50 轮 0.29 → 第 90 轮 0.16 → 第 99 轮 0.17 | 下降 | ✅ |

**已知偏差：** 换成公交的估计偏悲观，G 因此可能略偏低（偏保守）；公交被选为最好选项的只有约 0.5%。之后用实际经历的出行（`experienced_plans`）逐段排查。

**第 99 轮的 G（5% 样本，抽样种子 1，各运行是同一批人）：**

| 运行 | 种子 4711 | 4712 | 4713 | 均值 | 种子间 sd |
|---|---|---|---|---|---|
| 原版 RQ1 | 0.1661 | 0.1671 | 0.1658 | **0.1663** | 0.0006 |
| 精英父代 E1 | 0.1592 | 0.1587 | 0.1574 | **0.1584** | 0.0009 |

- 两者的路线差距都约 0.03，方式差距约 0.155–0.16；平均每人仍能好约 5 分（中位 2.3–2.4 分）。
- **E1 的 G 比原版低 0.008**，约为种子间 sd 的 9–13 倍：精英父代确实更接近均衡。这为 E1 "第二关不通过"（终点不同）给出了解释：它不是偏离，而是更收敛。
- **验收公式右边已经可以填：** Ḡ_原版(99) + 2·sd = 0.1663 + 0.0012 = **0.1675**。各运行用同一批抽样居民（按编号确定性抽样），抽样误差在比较中大部分抵消；若比较用的抽样不同，还要加上抽样误差（变异系数约 3%）。E1 的 0.1584 满足条件 ①。
- **W0**（热启动基线）的 G 待它的运行结束后计算。
