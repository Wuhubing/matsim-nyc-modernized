## 0. 一句话

## 3. 想做什么：补充记录分三层

### 第 1 层：9 个 run 全部加，体积小

1. 政策 run 也打开 `-Dnyc.replanningLog=true` 和 plan inheritance，得到和基线一样的 `agents/trips` 日志与计划谱系文件。
2. 扩展 `trips-IT`，记录创新的具体内容：
   - SubtourModeChoice：方式链前后对照（字符串）。
   - TimeAllocationMutator：每个活动结束时间的移动秒数。
   - ReRoute：路线长度和预计时间的前后差值。
   - trip 数对不上时也记录明细，不再一律写 -1。
3. `persons-N` 增加逐人**按方式**的出发数和完成数。
4. 计时：每轮按策略统计 replanning 耗时和 routing 调用次数，QSim、评分、选择各阶段分别计时。

### 第 2 层：9 个 run 全部加，每轮逐段执行记录

每轮写出 MATSim 的 `legs.csv`（每个 run 约 12 GB），可选加 `trips.csv`（再加约 6 GB）。日常的动态分析用这张表，不用每次都去解析 events。

### 第 3 层：9 个 run × 100 轮的 events

采用“**标准 events 加转换**”的组合方案：

1. 运行时用 MATSim 的标准 writer 写全量 events（XML.zst），不写新代码。
2. 每个 run 跑完后，转成紧凑列式格式：车辆过路段（车、路段、进入、离开），出行（人、方式、出发、到达、车辆），公交上下车，卡住，扣费；附上同一秒内的事件序号和 ID 对照表。
3. 校验转换前后的事件总数、分类型计数，以及和 `link-hours`、`group-modes` 的汇总一致。
4. 校验通过后，只在关键轮次保留 XML：0、10、20…90，49–50，78–80，98–99。其他轮次的 XML 删掉，只留紧凑版。

被动 events 只能给出相关性，不能证明“谁影响谁”，也不能做精确重放，因为 QSim 的队列状态和随机数状态都没有保存。因果问题之后要靠 checkpoint 加扰动实验。这一批重跑要保留关键轮次的全量计划作为 checkpoint；另外要核实 MATSim 每轮怎么重设随机种子，否则从 checkpoint 重启不一定能复现。

**ORCD 配额**（`~/orcd/.quota`，2026-11-24 12:25）：SCRATCH 848/1024 GB，POOL 831/1024 GB，**合计剩余约 370 GB**。

| 项目 | 依据 | 9 个 run 合计 |
|---|---|---|
| 第 1 层 | 实测：replanning 0.8 GB/run，谱系 0.7 GB/run | 20–35 GB |
| 第 2 层 legs（+trips） | 实测：118（+59）MB/轮 | 约 105（160）GB |

| 关键轮次的 XML（每个 run 约 17 轮） | 估算 | 170–260 GB |
| **组合方案长期占用**（第 1、2 层 + 紧凑版 + 关键轮次 XML） | | **约 600–800 GB** |
| 转换期间的峰值（正在处理的那一个 run 的全量 events） | | 约 110–170 GB |

每轮 1.1 亿个事件的来历：第 50 轮车辆进入路段 4630 万次（car 3150 万、taxi 820 万、FHV 660 万），每次进入对应进、出两个事件，再加上约 385 万段出行的相关事件。这个估算误差可能有 ±50%，要靠短测实测。

重跑的标准输出如果和原 run 逐位相同，核对通过后可以删掉，只保留新增的文件，不多占 175 GB。

**结论：组合方案需要先腾出约 400–600 GB**：向 ORCD 申请扩配额，或清理 `archive-2026-11-18`（旧方法实验，体积未查，删除不可逆，需要用户确认）。空间不够时的退路：只给 seed 4711 的 3 个 run 记录每轮 events，另外 6 个只记关键轮次。

## 5. 执行顺序和门槛

1. **立刻可做，不用重跑**：基于计划谱系文件做基线 Q2；读 `BUILT.output_config.xml` 确认 score 语义。
2. **建 branch，写代码**（见第 6 节）。本地编译，跑小规模自测。
3. **12 轮短测**，baseline、schema1、schema2 各一个，seed 4711，全部记录打开：
   - `persons-N` 的哈希列与原 run 前 12 轮**逐位一致**。对不上就逐项关掉记录，找出是哪一项改变了结果。
   - 实测每一层每轮的体积和额外耗时，events 尤其要测。
   - 跑通转换和校验脚本。
   - 规模：3 个短测，每个约 1–2 小时，共几十 GB。**需要用户批准。**
4. **按实测数字定存储方案**：扩配额或清理 archive，由用户决定。
5. **正式重跑 9 个 run**：约 1300 核时，另加记录开销。**需要用户批准。**
6. 每个 run 跑完：逐位核对、events 转换和校验、按规则删除 XML 和重复的标准输出。核对通过后，才把新数据和已有分析拼接使用。
